Checkpoint Comparison

Five policy checkpoints evaluated across 10 trials per task. Select a checkpoint to see its per-task success rates and a sample rollout video.

A fourth checkpoint, v4b run1, is deliberately not selectable here: its first evaluation scored 15% overall with 90% on exactly one task and 0% on every other — a pattern traced to two serving-time normalisation bugs (see What changed below), not a real capability result, and kept out of this comparison because it should never have been served that way.

What changed between checkpoints

pi05_base — Pretrained foundation model, no Baxter fine-tuning. Achieves 70% on T0 (red→far) showing strong transfer priors. Blue/green failure reveals colour-grounding limitation.
vel_99k — First fine-tune. Velocity-control action representation: policy predicts joint velocity commands directly. 4 tasks (no green). 100k steps. 0% success — gripper never closes; policy approaches but cannot grasp.
pos_200k — Switched to position control (predict target joint angles → P-controller converts to velocities). Added green block. 6 tasks. 200k steps. 20% overall; T2 blue→far gets 8/10 but mostly by pushing, not picking.
pos_v2 — Fixed demo recording: native 10 Hz (no downsampling). Added end-effector XYZ to state (8-dim → 11-dim). 500k steps. Final loss 0.004. 40% overall; block-lift rate doubles to 50%.
pos_v3 — Warm-started from pos_v2 (not from scratch). Lower peak LR (5e-5 vs 2e-4). 250 near-side demos per task (vs 100). 200k additional steps. Best overall result: 43% (26/60), 60% far-side average. Green (T4/T5) still 0% — traced afterwards to a demonstration dataset that had silently lost the green task entirely, compounded by a warm-start lineage that could not distinguish never having learned a task from having forgotten it.
pos_v4 — Trained fresh from pi05_base (not warm-started) on a freshly audited, complete six-task dataset (100 demos/task, all success-filtered). First non-zero result on either green task ever (30% far, 10% near) — but every red/blue task regressed (e.g. red-far 90%→70%) because 100 demos/task is less than pos_v3's 230–250. 38% overall: fixing green by construction traded away red/blue's earlier data advantage.
pos_v4b — Warm-started from pos_v4, scaled every task to its full success-filtered pool (1,464 episodes) via a six-way LeRobotMixtureDataConfig. run1's first evaluation scored 90% on exactly one task and 0% on every other — traced to two serving-time bugs invisible to training loss: the inference server silently defaulting to mean/std normalisation instead of the quantile normalisation $\pi$0.5 requires, and a one-normalisation-per-session design that was wrong for six tasks sharing one robot. Fixing the first alone (no retraining) took task 0 from 0/10 to 9/10; fixing the second required a full retrain (run2) against one pooled normalisation. run2 reached 41.7% overall with every one of six tasks non-zero for the first time, including a best-yet 70% on green-far.

π0.5 — Vision-Language-Action

π0.5 is built on PaliGemma (2B VLM) with an added 300M action expert communicating via cross-attention at every transformer layer. It generates actions via flow matching — denoising Gaussian noise into a 10-step action chunk.

xt = t · ε + (1 − t) · a
ut = ε − a
ℒ = MSE(vθ(xt, t, obs), ut)

VLM Stack

A Gemma-3-12B planner sits on top of the low-level policy, converting a goal image into an ordered sequence of manipulation primitives and closing the loop with a goal-check / re-plan cycle. This design was arrived at after an earlier pilot (GroundingDINO detection vs. free-form Gemma monitoring on a real-world sorting task) showed that Gemma's structured, multi-object output was unreliable — the per-block querying strategy below sidesteps that failure mode directly.

🗺️

Per-Block Task Planner

Gemma-3-12B-IT

Receives the current scene image and a goal scene image, and queries the model once per block colour rather than once for the whole scene — each query is restricted to a single object with a strict two-line (current: near/far / goal: near/far) answer format. This avoids the multi-object binding errors that a single combined query produced during earlier testing. Mismatched blocks are appended to an ordered primitive list.

Inputcurrent + goal images, per colour
Outputordered primitive list
Goal space2³ = 8 near/far configurations
🔁

Closed-Loop Goal Checking

Gemma-3-12B-IT

A second, independent yes/no query checks whether all three blocks already match the goal — used both before planning starts and after every executed primitive. If the goal isn't met, the scene is re-rendered and the plan → execute → check cycle repeats (up to 3 rounds). This is the mechanism that will detect and react to a human repositioning a block mid-task in the planned collective-task evaluation.

Human-Robot Collaboration: Escalation-Based Task Allocation

The VLM planner and fine-tuned policy were combined into a working collective task: a multi-block rearrangement is decomposed into subtasks, each attempted autonomously, and handed to a human operator only once a fixed autonomous-retry threshold is exhausted. This is a deliberately narrower mechanism than free-form collaboration — its necessity is itself evidence of the execution fragility documented throughout this project.

🖼️

Bug 1 — Planning Wasn't Grounded

The planner's original image-based scene comparison was found not to work at all: swapping which of two rendered images was labelled "current" vs. "goal" produced identical planner output, proving the model wasn't grounding its judgement in the images for this task. Switching to ground-truth symbolic state resolved planning outright — every subsequent test run generated the correct, minimal primitive list.

📐

Bugs 2 & 3 — Execution, Not Planning

Even with planning fixed, full-pipeline runs still reached 0/3 and 0/1, 0/2 planned subtasks — a failure rate improbable enough (~1-in-70-million for one six-task run, given the policy's own validated 30–70% per-task rate) to demand investigation. Traced to: the simulation runner feeding the policy an 8-dim state instead of the 11-dim format every other evaluation uses, and the arm resetting to home only once per session instead of before every subtask.

🎬

Bug 4 — Out-of-Distribution Scenes

Multi-block scenes place every block that needs to move away from home simultaneously — a composition absent from every training demo and single-task eval, which only ever move one block. Resolved by a rendering-only fix: showing non-target blocks at their home position in the image fed to the policy, while every other part of the system uses their true position. No retraining required.

🤝

The Resulting Mechanism

With all four fixes in place: subtasks are attempted autonomously; on repeated failure, the system flags the subtask and hands it to a human operator; once ground-truth state confirms the human completed it, autonomous execution resumes on the remainder. No case observed of the system failing to detect a resolved escalation or resuming incorrectly. This is a blind retry-count trigger in the execution loop, not VLM-mediated semantic judgement.

📋
Scope, honestly stated: this is a working demonstration of escalation-based task allocation on representative multi-block configurations, not the larger systematic trial matrix originally proposed. That matrix is recorded as outstanding work in todo.md, together with the infrastructure (checkpoint, display, launch script) confirmed ready to run it. Every genuine execution failure found while building this system traced to a specific, identifiable cause — mirroring the same pattern documented for the single-policy checkpoints above and the cross-embodiment extension below.

⚠️
run2 is not simply better: G1 gained genuine new capability (blue-near and green-near, both previously untestable, reached 40% and 30%), but on every task both checkpoints could attempt, run2 scored meaningfully worse — Franka's overall success nearly halved. Five to six times more training data plus a genuine correctness fix produced a worse policy on the tasks that already worked. Not diagnosed further within this project's scope; candidate causes include a shifted near/far task balance and a learning-rate schedule tuned for a much smaller dataset. Reported here honestly rather than smoothed over, matching the wider pattern documented throughout this project.
🔧
Reach-margin methodology: most cross-embodiment failures traced to a specific, fixable cause rather than a vague "embodiment difference" — G1's wrist camera was mounted to the wrong parent frame, G1 self-collided against its own locked torso, Franka's first pass derived an invalid grasp orientation from an unconstrained IK search, and both robots hit genuine base-position reach trade-offs. Each was diagnosed and fixed individually, producing the corrected datasets used for run2 above.
🎯
The question this section set out to answer — does a single policy trained jointly across all three embodiments transfer skill positively or negatively relative to the solo policies above — remains open. The joint retrain (corrected data, normalisation bug fixed) is in progress, roughly 187k/300k steps at time of writing. This comparison was invalidated twice before reaching this point — first by incomplete training data, then by the normalisation bug — which is itself a finding about how hard this kind of claim is to measure reliably, not only about the eventual transfer outcome.

Real Robot Deployment

Moving the fine-tuned policy from MuJoCo onto a physical Baxter robot, split into two results: a direct simulation-to-real transfer test of the strongest simulation checkpoint, and — motivated by that test's failure — a separate policy fine-tuned from scratch on real kinesthetic-teaching demonstrations, bypassing simulation entirely.

Two-Machine Split

A remote control laptop runs ROS Indigo + baxter_interface (Python 2.7), with direct access to joint state, gripper state, and the wrist camera. A separate GPU lab PC runs the policy server, with an Intel RealSense camera attached directly to it for the workspace/scene view — captured locally and injected into the observation, rather than routed through the laptop.

⚠️
The 54% figure is a measure of reliability near the training distribution, not of generalisation. Found only after running the evaluation: every trial's block placement fell within ~17.5 pixels of the training dataset's own placement cluster (itself only 4px std, in a 224px frame), despite an intention to vary placement across trials. Whether this policy generalises to new block placements remains untested — direct real-data fine-tuning is reported here as a viable, if narrow, alternative when simulation-to-real transfer does not hold, not as a solved generalisation result.
